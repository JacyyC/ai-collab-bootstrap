# AGENTS.md

本文件是人类与 AI 的日常工作协议。Skill 仅在首次建立、对齐或获取更新后升级工作区时使用；日常无需加载 Skill。客户端专用入口可引用本文件，不复制第二份协议。[文档政策](workspace/docs/DOCUMENTATION_POLICY.md)规定内容归属，[生命周期](workspace/docs/DOCUMENT_LIFECYCLE.md)规定记录格式；只有修改相关规则或遇到边界问题时才读取细则。

## 接手

1. 读本文件、[WORK](workspace/docs/WORK.md)和选定工作项的 README；重新查询 Git 状态，识别用户既有改动。
2. 首次进入项目或项目定位发生变化时读根 [README](README.md)；范围、实施、架构、历史按当前问题读取对应正文，不全量读取导航登记表和旧日志。
3. 阅读、解释和状态查询不建立工作项。实施时使用已有相关工作项；没有合适记录时建立最小工作项。

## 工作与记录

- 用户确认的范围和验收条件先明确；实现与验证不能为了提前结束而缩减范围。
- 小任务在工作项 README 写目标、边界、AC、必要决定和验证；多阶段或复杂任务按需拆 Spec、Plan、Log、Evidence。
- 工作项只填写本次事实和必要入口，不复制整套协议。字段更新、附件归类和真实章节链接可用本地维护工具，命令集中在 [Lifecycle](workspace/docs/DOCUMENT_LIFECYCLE.md#机械字段、附件与链接)。
- 新授权、范围变化与返修安排先回流现有范围/计划章节或 Spec/Plan，实际结果进入验证章节或 Evidence；更新现行段落，不追加多份“最新授权/当前技术门”。README 保留当前入口，重要变更原因进入 Log。归属见 [Policy](workspace/docs/DOCUMENTATION_POLICY.md#现行约定与历史依据)。
- 仅为需独立保存、引用或复核的专题、原件和完整报告新建文件，按 [Lifecycle](workspace/docs/DOCUMENT_LIFECYCLE.md#文件组织与命名) 分类、命名并建立入口；不按轮次或阶段另建总结副本。
- 状态、Stage、下一步只维护 README YAML；正文补充原因、风险与交接背景。详细规则见 [Lifecycle](workspace/docs/DOCUMENT_LIFECYCLE.md)。
- 普通实施不逐命令写文档；可交接检查点、暂停或完成时更新当前记录，稳定能力或架构改变时同步实际受影响正文。
- 完成前对照 AC 与实际结果。没运行的检查写未运行，工具结构检查不能替代业务验收。
- 首败、后续验证和适用源码/输入保持可追溯；项目内提供原件入口，外部保存的内容说明身份和访问限制，不能仅依赖临时观察目录。
- 检查点执行一次 `python3 workspace/scripts/maintain.py --checkpoint <ID>`；审查用 `--check`，不写文件。失败时修复或如实记录阻塞，不宣称完成。

## 修复与验证

- 原因明确、影响局部且风险较低的问题定点处理；原因不明、跨模块、高风险、修复后复发或既有能力回退时，按证据扩大到相关调用链、依赖和合同，重新评估原因与方案。处理深度随影响调整，见 [Lifecycle](workspace/docs/DOCUMENT_LIFECYCLE.md#按问题范围修复与验证)。
- 按变更影响选择验证，核对已有结果的适用依赖，复用仍有效的依据并补验受影响部分；反复问题兼顾相邻反例与需要保护的能力。无新证据或可检验假设时转向诊断、调整方案或报告阻塞，不重复试到偶然通过。
- 修复依据真实业务或技术合同，不针对题号、样本或预期答案塞特例，不靠放宽校验掩盖失败。经验优先回流适用的测试、合同、配置或说明；记录沿用当前工作项，归属见 [Policy](workspace/docs/DOCUMENTATION_POLICY.md#修复经验与验证复用)。

## 代码与文件布局

- 已有项目沿用根 README 明确或链接的目录职责。每次新增、生成或移动源码、测试、脚本、配置和运行资产前，读取相关模块入口与相邻实现，先判断能否复用，再确定归属与目标路径；细则见 [项目文件布局](workspace/docs/PROJECT_LAYOUT.md)。
- 运行代码按模块职责进入项目区；`workspace/scripts/` 只放协作治理工具，工作项只记录过程与证据并引用实现。临时验证代码需明确删除、归位或保留用途，不能持续散放。
- 源码、测试、配置、工具和资源目录内部也按实际模块边界、层次或用途分类，命名遵循技术栈并表达职责；需并存或留存的版本明确含义，普通迭代更新现行实现，不按工作项或轮次复制代码。
- 新目录或职责变化同步对应 README；检查点前核对本任务新增、改名和未跟踪文件，覆盖已提交的任务内变化，检查分类、命名、版本与重复实现。移动后修复引用、测试发现并实际验证；工具结构检查不代替此项审查。

## 边界与安全

- 业务代码、测试、配置、产品与架构说明沿用项目实际入口；`workspace/` 保存工作记录、项目内模板与治理工具。架构事实、已接受目标和候选设想明确身份，默认不创建 project/ 或 framework 空骨架。
- WORK、HISTORY（以及已有旧工作项管理入口）由工具生成，不手工修改受控区块。同一事实只维护一处；新增或移动稳定说明时更新其权威入口与实际引用；已有登记表按本项目约定维护。
- 不回退用户或协作者改动；密钥、私人数据、数据库、缓存不进入仓库。根 `开发日志.md` 仅供人工，未经针对该文件的明确指令不得改动。
- 既有 Schema 2/3 与历史记录保持可读，新项使用 Schema 4；已完成/取消记录默认冻结，纠错写日期、原因与依据。
- 工具不自动提交、重置、部署或把工作项标为完成。产品范围、持续付费、第三方权限、生产部署、公开发布及不可逆操作按用户授权处理。

## Git

Stage 是实施与验证检查点，完成不以提交为前提；交接必须如实记录未提交状态。大规模移动前确认有可回退提交。未获明确授权不提交、不推送、不变基、不强推。

获授权后只暂存本任务文件，检查完整 diff、验收证据和统一门禁。提交首行用 `[已登记ID[/工作项已定义Stage]] 简洁中文动宾短语`；多项用 `[ID1+ID2]`，一次性非工作项维护用 `[misc]` 并说明目的。阶段起点 `head` 不回填为包含自身记录的提交哈希。

## 治理来源与升级

模板指纹：`<TEMPLATE-FINGERPRINT>`；记录 Schema 与清单格式不是具体发行身份。实例化时在本处补来源修订（可得时）、实际采纳范围、保留定制及未合并差异，详细过程引用本次升级记录。来源未知如实标注，不据此猜测旧版本。

升级完整 Skill 包与升级本项目是两步；后者需合并本地协议、三份规则、五份模板、创建回退、工具和导航。保留项目事实、定制、用户改动及终态原件，不能用模板整页覆盖。客户端薄入口只引用本协议；接入一次后不复制第二套规则。

升级本身单独记录，已有工作项及其原件默认只读，新规则由后续任务采用；针对旧记录的明确更正指令另按其范围处理。范围、状态、证据、工具各自合并到实际入口，部分采纳和未知旧来源如实说明。

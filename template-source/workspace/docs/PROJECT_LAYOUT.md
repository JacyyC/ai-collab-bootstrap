# 项目文件布局、分类与命名

目录约定适用于初始化和后续每次新增、生成或移动文件。根 [README](../../README.md)明确项目区、工作区与根级入口，并链接实际模块的职责说明；项目区可沿用既有 `src/`、`tests/` 等布局，不要求统一搬到 `project/`。本页规定归位方法，实际路径以项目入口和实现为准。

## 适用范围与判断方法

本规则适用于单体、多包、多服务及不同技术栈的项目文件，不预设必须采用哪种分层、目录名或版本号。新增类别也按以下维度判断，不以文件扩展名或某个示例目录替代归属判断：

1. 职责与使用者：它实现什么、由谁调用或读取，是运行源码、测试、配置、工具、资源、文档还是结果？
2. 所属边界：它属于哪个模块、包、服务或交付目标，是局部使用还是确需共享？
3. 既有约定：相关模块如何组织，语言、框架、构建、测试发现和部署对位置与命名有什么实际要求？
4. 版本与生命周期：是否存在需要区分的合同或发布版本；内容是维护中的源文件、可再生成文件、临时实验还是冻结依据？

依据这些事实选择位置与名称。模块共置、按层分目录、按业务域分包等方案可以各自成立；沿用项目已采用且职责清楚的方案。工具要求固定位置、跨模块共享或混合技术栈时保留实际约束，在所属入口说明；不为套用示例而重塑架构。

## 创建前确定归属

先读取本次涉及的目录职责、相邻实现、包配置和运行入口，判断已有模块或工具能否承载变更。修改已有实现即可完成时，不另建同职责脚本或平行实现。确需新文件时，先明确用途、所属模块、目标路径及调用或运行方式，再写入；不能先散放在根目录、工作项或通用 scripts 目录，留待收口时再整理。

按文件的长期职责选位置，不按本轮工作项、Stage、日期或执行次数组织运行代码：

| 文件职责 | 归属依据 |
|---|---|
| 业务源码、运行配置、数据库迁移、静态资产 | 对应项目模块及框架已有约定；遵循包、构建与部署边界 |
| 单元、集成、端到端测试及测试夹具 | 项目现有测试组织方式；允许同模块共置或独立 tests，不另起一套布局 |
| 开发、运维、数据修复、演示、评测与复现脚本 | 按用途进入已有项目工具、测试或独立演示区；不能因为由某工作项产生就放入工作记录 |
| Workspace 维护与检查工具 | `workspace/scripts/`；该目录不收纳业务运行、业务评测或数据修复代码 |
| 执行日志、截图、机器结果、完整报告 | 按 [Lifecycle](DOCUMENT_LIFECYCLE.md#文件组织与命名)进入工作项分类/批次附件，或登记项目已有产物位置 |
| 一次性探针、临时实验与生成的代码 | 探针使用项目约定的临时区；需继续运行或复用的源码归入对应模块、测试或工具。代码生成器的输出指向其约定生成目录，不因自动生成而免于归位 |

工作项保存范围、计划、决定与验证依据，通过路径或链接引用实现。确需留存的历史源码快照可作为不可变证据，不得充当现行实现的导入、构建或部署依赖；作为历史兼容测试输入时明确夹具身份，不成为继续修改的第二份源码。

## 目录职责与持续更新

同一职责优先复用已有目录。确有新模块或新职责时，在任务范围内创建最小必要目录，使用项目既有命名方式；不以临时、final、latest 或工作项编号替代长期职责命名，也不预建尚无用途的目录。已有包名或外部合同涉及这些名称时先保护兼容性，不能只按名称批量改写。

根 README 维护顶层边界；模块入口维护内部职责。新增顶层目录、改变模块职责或形成新的长期工具入口时，同步对应入口，说明实际路径、用途与必要运行方式。普通文件由目录职责覆盖，不逐文件登记，也不为本规则建立另一份文件台账。框架或工具要求位于根目录的配置与启动文件可以保留，在相关入口说明其用途。

运行命令、测试和生成器有输出路径参数时，在执行前指向该类文件的约定目录，避免日志、结果、缓存和生成源码随启动位置散落。生成文件通过生成源、配置或输出参数维护，不为归位手改生成副本。一次性代码在验证后按实际用途删除或归位，保留必要结果与历史失败依据；依赖、缓存、本地数据和密钥遵循项目排除规则。

## 目录内部分类与命名

进入源码、测试、工具或资源的顶层区域只是第一层归属。同一目录包含不同业务域、技术层次、运行用途或兼容合同，已经需要靠反复添加长前缀才能区分时，按实际职责建立子目录。新增文件先检查这一层，不持续把不同类别平铺在公共目录；已有混合布局的整理仍按任务授权处理。以能定位职责、控制依赖和独立验证为准，不设固定文件数或目录深度。

同层选择清楚的主分类轴，再按需要细分，避免业务域、工作项编号与时间等不同含义混杂。下表给出判断依据，不规定各项目必须采用同一棵目录树：

| 范围 | 分类依据 | 维护重点 |
|---|---|---|
| 源码与模块 | 项目已有的能力/业务域、技术层或包/服务边界 | 模块内继续按职责分类；共用抽象仅在实际复用时提取，避免把无关实现堆入共享目录 |
| 测试 | 项目采用的被测模块、测试层次或运行环境；可共置，也可集中管理 | 名称表达被测行为或合同；工作项编号通过记录关联，不作为长期测试分类的唯一依据 |
| 测试支持与数据 | 使用范围、合同、场景与数据身份 | 共享辅助逻辑进入明确支持入口，避免测试文件互相依赖；局部夹具不无故提升到全局 |
| 项目工具 | 开发、运维、评测、迁移等实际用途及所属模块 | 入口名称说明动作与对象；不把无关脚本持续堆入通用工具目录 |
| 配置与资源 | 消费它们的模块、构建/运行目标、平台或环境 | 跟随实际加载和打包边界，环境/平台变体名称与版本含义分开；框架要求共置时遵循框架 |
| 生成文件与产物 | 生成源、使用者及保留要求 | 源文件和输出身份明确；可再生成、需留存与本地排除内容各按既有合同维护 |

目录名说明稳定领域或层次，文件名说明该目录内的具体职责或行为，避免重复叠加目录已经表达的前缀。大小写、分隔符、文件后缀与发现约定遵循所属技术栈及项目规范；不把某种语言的模块规则或工作项 topics 的连字符规则套到所有文件。已有公开导入名、CLI 名称、资源身份和框架约定优先保持兼容。

## 版本与兼容边界

需要区分的版本必须有实际合同依据，例如同时支持的 API/协议版本、不同数据格式、数据库迁移序列或明确保留的发布验收套件。通过目录、文件名或框架的显式版本机制表达边界，并在相关入口说明适用版本、对应实现/合同、共享部分与退出条件；测试数据及夹具沿用同一版本含义，不能只写 v1/v2 而不说明指什么。

- 并行兼容的实现、测试与输入数据，在对应职责范围内区分合同版本，保持调用方选择明确；版本可通过目录、文件名或框架已有机制表达。跨版本不变的行为复用共同实现、测试与支持模块，避免复制整套源码或测试。
- 明确保留的发布验收套件说明发布范围、适用实现基线和运行条件；历史套件与现行回归分别选择，不能把旧实现专用测试默认当作当前版本验收。
- 数据库迁移沿用框架的有序版本标识；已执行的迁移与冻结夹具按其历史合同保存，新变化新增迁移，不能覆盖旧历史。
- 普通重构、返修和同一现行合同的迭代更新原实现与对应测试，Git 保存先后版本。工作项/Stage、执行批次和产品/协议版本分别记录，不能把工作项编号、轮次或日期直接当作兼容版本，也不生成 final/latest/new 等并存实现。

版本目录用于表达真实并存或留存边界；先后已替代的代码是否保留、历史验收如何运行依项目合同和用户范围处理。新增版本必须补充相关运行、测试选择与兼容验证，不能仅改目录名就宣称隔离完成。

## 检查点核对

暂停、交接或完成前审查本任务新增、生成和改名的文件，不能只看已跟踪文件：

- 有 Git 时，读取 `git status --short --untracked-files=all` 与 `git diff --name-status --diff-filter=AR HEAD`；存在有效工作项起点时，再核对相对该基线的变化，覆盖本任务已经提交的新增文件。无 HEAD 时直接检查暂存区和未跟踪文件；无 Git 时按开始时的目录事实核对，不伪造差异检查。
- 对照接手时的用户改动，识别本任务文件，逐项核对模块内分类、命名、版本含义、调用入口、是否重复实现及临时代码去向。文件在项目区内不等于模块归属正确；工作项或 artifacts 中有合法入口也不能证明可运行代码放置合理。
- 移动文件后修复实际受影响的导入/包导出、测试支持配置与辅助模块路径、测试发现及同名模块冲突、命令、资源加载、构建、CI、部署与生成/读取路径，并运行相关测试或构建；比较迁移前后的测试收集范围，防止测试搬走后未被执行却显示通过。发现既有杂乱而超出本次整理范围时保留原文件，记录缺口，不扩大搬迁。
- 在当前工作项的验证或交接中简述归位审查结果和未解决问题；目录职责变化同步原入口，不另建逐轮布局报告。检查失败时修复本次新增内容或如实交接，不能只改目录说明来合理化误放。

`maintain.py` 检查工作项布局、文档、链接与 Git 差异空白，不自动判断项目代码的职责、重复实现或临时代码用途。上述代码归属审查由执行者结合实现完成；结构检查通过不能代替它，也不能代替业务运行验证。

# Workspace 文档生命周期

本文件定义工作记录与检查合同；内容归属见 [Policy](DOCUMENTATION_POLICY.md)，执行权限见根 [AGENTS](../../AGENTS.md)。

## 记录与状态

工作项永久位于 `workspace/docs/work-items/records/<小写稳定-id>/`，不随状态搬目录。状态为 `planned`、`ready`、`active`、`blocked`、`paused`、`completed`、`cancelled`。完成和取消均有关闭日期及可复核依据；非终态不带关闭日期。

README YAML 是状态源，WORK、HISTORY 和工作项管理页仅为派生视图。小项在 README 保存目标/边界、AC、必要决定、验证与限制；内容较多时分别拆 Spec、Plan、Log、Evidence。没有内容时不预建空文件，不增加“选轻量还是完整”的问答。

## Schema 4

新建项使用 Schema 4。README 必需字段为 `schema_version`、`document_status`、`last_updated`、`id`、`title`、`status`、`updated_at`、`next_action`；终态另有 `closed_at`。

| 字段或内容 | 合同 |
|---|---|
| id | 大写语义 ID，如 `V1-01`、`DOCS-01`；目录为对应小写；不得复用 |
| priority | 可省略，默认 P2；值为 P0 至 P3 |
| stage | 无分阶段时为空/null；非空时引用 Plan 或 README“计划”内实际定义的 Stage ID |
| depends_on / blocked_by | 可省略，默认空；依赖须存在且无循环，外部门禁用 G-* |
| spec / plan | 可省略；默认内容在 README，分文件时链接实际正文；共享 Spec 可引用 records 下另一已登记项的 spec.md |
| head / branch / created_at | 新建工具自动记录；head 是工作或 Stage 起点基线，检查点不得覆盖。没有 Git 时明确 none |
| labels / framework_scope | 可省略，按检索需要填写 |
| next_action | 只在 YAML 维护一次；终态说明结束后的动作或无后续动作，不复制到快照/交接表 |

范围、AC、决定和验证是实际内容，不由生成器替人确认。planned 项可保留待明确内容；实施前填写实际目标和验收条件，不能用真实活动/终态项的占位符冒充完成。

验证记录可在 README“验证”或独立 Evidence，使用 `AC-01` 等编号、实际命令/证据、`passed`/`failed`/`not_run`/`pending` 状态及限制。工具只运行结构检查，不验证证据叙述真实性；completed 所有已声明验收条件有通过依据，不能有明示未通过条件或只有空文件、全部 pending。同一 AC 有重试记录时，以最后一条为当前结论，保留历史失败。取消说明原因、验证到哪里和未覆盖范围。

## 按需拆分与影响

范围复杂时建立 Spec，跨阶段实施时建立 Plan；过程或证据妨碍接手阅读时才拆 Log/Evidence。范围、实施步骤与结果分别维护，避免重复权威正文。

### 文件组织与命名

创建文件前先按 [内容归属](DOCUMENTATION_POLICY.md#现行约定与历史依据) 回流已有章节；只有内容需独立保存、引用或复核时才拆分。新建时明确用途、分类、命名和入口，不以对话轮次、执行次数或固定文件数量决定。不预建可选文件或目录。

| 位置 | 用途与约定 |
|---|---|
| `README.md` | 必需入口，保存状态源、范围与导航；单页足够时不拆分 |
| `spec.md` / `plan.md` | 按需保存范围与 AC、实施计划；README 通过正文链接或对应 YAML 字段指向正文 |
| `log.md` / `evidence.md` | 按需保存重要决定与过程、验证依据；README 必须有正文链接 |
| `topics/` | 确需独立阅读的专题正文；目录和 Markdown 文件使用小写英文、数字与连字符，如 `topics/data-migration.md`；每页从 README 直接链接并简述用途 |
| `artifacts/<类别或批次>/` | 授权原件、日志、截图、完整评审与执行报告等独立附件；目录使用小写英文、数字与连字符，文件沿用工具或项目既有命名；从 README 或其链接的正文进入目录或关键产物，说明用途 |

工作项目录顶层仅维护约定正文，JSON 等机器结果也不散放顶层。阶段计划、总结、交接与复核优先写为已有章节，不滚动生成同类副本；topics 与 artifacts 不用于隐藏重复的现行计划或工作日志。稳定产品说明归入项目文档，跨工作项长期决定按文档政策归入 ADR，不为集中存放而复制到工作项。

例如授权原件放 `artifacts/authorizations/2026-11-02-scope-extension.md`，某阶段候选的执行和评审放 `artifacts/r4/c10/execution.json`、`artifacts/r4/c10/quality-review.md`。同类产物在不同批次内沿用稳定文件名，完成的批次保持原件与失败记录；返修安排回流现行计划，技术复验属于自己的批次，不覆盖旧执行结果。专题沿用实际职责命名，不堆叠 final/latest/v2 等现行副本。

产物入口登记所属阶段或批次、用途、适用源码/输入、结果与原件位置，优先复用现有报告中的身份和哈希字段；多文件需要清单时复用已有索引或生成批次清单，不再维护第二套状态与授权账本。产生工具有输出目录参数时统一指向对应批次，工具可维护产物索引区，正文验收结论仍由执行者核对。小型可审阅报告和清单按项目约定进入 Git；大型或受限原件登记实际保存位置和保留要求，不为集中归档搬运私人数据。迁移时检查生成工具、读取工具、固定路径和哈希核验，保留原件内容，不靠重跑重建历史证据。

维护入口对非终态、非归档的 Schema 4 项检查文件布局、分类目录、专题命名及入口；附件入口可位于 README 或其直接链接的正文，避免 README 展开每轮详细产物。原始文件沿用既有命名，`.gitkeep` 和 `.DS_Store` 不作为工作记录检查。检查覆盖未跟踪文件，报错时保留原文件，不自动移动、合并或删除。独立用途、现行约定是否完成回流、证据是否仍适用、重复内容、入口说明和保存要求由执行者审查；工具不按标题关键词或章节数量判断这些语义。Schema 2/3、已关闭项及项内 `archive/` 保持历史合同；不得为通过新规则把活动记录塞入 archive，或提前关闭、归档工作项。

Schema 4 Plan 可声明 `impact_schema: 2`（省略时按新格式处理），文档影响只列实际受影响页面、处置和原因；无影响写“无”。计划中的 Stage ID 如 V1-01A，README 当前 Stage 必须能定位到定义。共享 Spec 不意味着实施上依赖其所属工作项，依赖字段只表达实际前置成果。

## 历史兼容

Schema 2/3 保持原文件和字段合同，终态默认冻结，不批量升级。Schema 2 的 base_head 继续兼容；Schema 3 使用 head、Plan impact_schema: 1 和原十类 DOC-* 影响矩阵。新任务使用 Schema 4，旧活动项只有需要实质改造时才迁移，记录原因。

历史终态有 Evidence；明确 archived 的 Legacy 可保留 source.md.txt 及局限。新格式的内嵌证据不用于静默删除旧证据文件。

## 按问题范围修复与验证

按原因确定程度、影响边界、复发情况和风险选择处理深度，不按代码行数、文件数量或统一失败次数划分。已有项目规定的验收、授权与预算边界继续生效。

| 情况 | 处理与验证 |
|---|---|
| 原因明确、影响局部且风险较低 | 定点读取相关实现与依据，做必要修复并验证受影响行为；当前工作项简述结果 |
| 原因不明、跨模块、高风险、修复后复发或此前通过的能力回退 | 围绕相关调用链、共享依赖、输入和合同扩大诊断，区分已知事实与待验证假设，重新评估方案及验证范围 |

诊断范围从故障点沿证据扩展到相关模块与依赖，需要时检查共同机制、配置、环境或验证方法本身，不默认全仓审计。高风险问题即使改动很小也提高检查深度；相同表象不自动认定同一根因。原假设被反驳、影响不断外溢或修复反复失效时先重新评估，再决定下一组改动；每组改动有可解释的目的，避免多项无关变化混在一起而无法归因。无新证据或可检验假设时停止重复修改和运行，转向诊断、调整方案或如实报告阻塞，并继续不依赖该阻塞的授权工作。范围扩展超出已有授权时按根协议处理。

验证按实际依赖、风险与项目既有要求选择，相关旧依据的复用见 [Policy](DOCUMENTATION_POLICY.md#修复经验与验证复用)。反复问题检验原失败、相邻反例及需要保护的既有能力；是否补自动回归由复发风险、可验证性与维护成本决定，不为每个小修复强制新建测试或复盘。必要时扩大到集成、构建或运行验证，项目明确要求的检查仍需完成。存在随机输出或外部波动时，结合受控比较和必要的稳定性观测判断；单次通过只证明该次结果，不能自动宣称稳定修复，也不能拼接不同候选的成功子集作为同一次验收。

固定协议、合法业务常量及明确边界可正常实现；新增逻辑应由实际合同支持，不能依赖特定题号、样本身份或已知期望答案来迎合验证。通过相邻反例或独立输入核对疑似特例的适用范围。测试、数据或验收本身有误时依真实合同及相应授权更正，记录依据和影响；不能暗改阈值、删掉有效失败或跳过检查来取得通过。工具结构检查不自动判定问题大小、根因、修复泛化或证据适用性。

诊断沿用当前工作项及现有状态源，不另建进度表、问题编号体系或逐轮“最新方案”。小项在 README 相关章节保存必要判断；复杂项按职责回流 Spec/Plan/Log/Evidence，只有信息确需独立保存时才拆分。记录与经验的具体归属见 [Policy](DOCUMENTATION_POLICY.md#修复经验与验证复用)。

## 检查点

1. 实施前明确范围与 AC；多阶段项当前只推进一个明确 Stage。
2. 普通实施按需留下重要决定或阻塞，不逐命令写日志；修复深度与验证按[问题范围](#按问题范围修复与验证)调整，新增或生成运行文件前按 [项目文件布局](PROJECT_LAYOUT.md)确定归属与目标路径。
3. 可交接点、暂停或完成时，核对任务内新增、改名与未跟踪文件的归属及临时代码去向，更新当前状态、必要背景、实际验证及限制，并同步发生变化的稳定事实。
4. 执行 `python3 workspace/scripts/maintain.py --checkpoint <ID>`，一次刷新视图、检查工作项/文档/链接和 Git diff，并记录工具本次结果。失败先修复或保持未完成，如实交接。

只读审查用 `python3 workspace/scripts/maintain.py --check`，不写视图或记录。新建用 `--new <ID> --title <标题>`，只生成单页规划项及机械字段。工具不提交、不重置、不自动改业务完成状态；工具检查块不作为业务 AC 证据。对终态执行检查点只更新派生视图和输出结果，不修改已冻结正文。

Stage 是可验证实施单元，与 Git 提交独立。未授权提交时保留真实未提交范围；授权后按任务范围提交，不为回填提交自身哈希另建提交。

## 稳定文件与架构

稳定页有 document_status 与 last_updated，只有事实成立才作为 active 权威；draft 可保留模板提示。历史废弃/替代正文声明替代入口或原因。

Current 默认一页，先说明覆盖、已验证能力和限制；需要时拆 Technology、Components、Flows、Data Integration、Verification。Target、ADR、Roadmap 在产生已接受目标或长期决策时建立；没有需求时不填假事实，也不要求这些可选目录存在。删除可选骨架须同时修复链接和登记。

新增/移动/删除稳定页时更新登记与入口，完整检查覆盖真实链接、孤立页与状态。跨仓检查仅在实际跨仓变更时触发，不规定无条件“两仓每周检查”或每次人工三路径走读。

## 模板维护

本仓库的 template-source/ 是模板源，skills/ai-collab-bootstrap/templates/ 是发行副本；实例化项目只有自己的工作区，不维护这一对源与副本。模板规则或工具变化后运行回归，再执行模板维护仓根目录的 `python3 scripts/sync_templates.py --write` 和 `--check`。这是模板发行操作，不是实例化项目日常任务的额外步骤；不得复制真实工作项、用户文档、人工日志和私人数据。

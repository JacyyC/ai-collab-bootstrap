# 文件分类规则

重构或定位归属不清的文件时读取本文件。分类用于提出整理建议；内容归属最终以目标项目的文档政策为准，新项目参照 [Policy 模板](templates/workspace/docs/DOCUMENTATION_POLICY.md)。文件名、目录和关键词是信号，不是完整事实。

## 扫描与排除

只扫描本次授权目录。保留 `.git/`、依赖与构建缓存、外部仓库和指向仓库外的符号链接边界，不向外追踪或迁移。

- 不读取或搬运 `.env*`、密钥、证书私钥、凭据、私人数据和本地数据库；对可能命中的文件只说明需人工判断，不能仅凭名称认定敏感内容。
- 跳过 `node_modules/`、虚拟环境、`__pycache__/`、`dist/`、`build/` 等实际缓存或产物目录。依据目录用途排除，不能把治理文档的 `framework/target/` 当成构建产物。
- 项目所需图片、字体和其他二进制资源属于项目资产；迁移目录时保持相对关系，不需要读取其内容。
- 工具配置如 `.trae/`、`.cursor/`、`.vscode/` 通常保留原位；不能把 Skill 自带模板、用户笔记或编辑器配置混入业务记录。
- 根人工开发日志遵守项目协议，不能纳入默认整理或拆分。

## 分类信号

先看文件职责与明确入口，再看目录、名称与内容。通常按下表判断：

| 文件职责或信号 | 建议归属 | 判定边界 |
|---|---|---|
| 源码、测试、运行配置、包管理、数据库迁移、静态资产 | 项目侧，优先保留现有布局 | 只有完整重组范围涵盖这些文件时才移动 |
| 安装、使用、API、运维、FAQ、面向用户的发布说明 | `project/docs/` 或项目既有文档区 | 稳定事实，不写工作项状态和交接 |
| 工作目标、范围、验收条件、当前进度、下一步、阻塞 | `workspace/docs/work-items/records/<id>/` | 先识别所属工作项，不能凭文件名发明 ID 或状态 |
| 路线顺序与跨工作项依赖 | `workspace/docs/ROADMAP.md` | 单项状态保留在工作项 README |
| 跨工作项的长期技术取舍 | `workspace/docs/decisions/` | 只在确有长期决定时创建 ADR；局部过程决定留在工作项 |
| 已实现内部架构 | `workspace/docs/framework/current/` | 核对代码、配置或运行证据后进入 Current |
| 已接受但未实现的目标架构 | `workspace/docs/framework/target/` | 明示目标身份，不宣称已经实现 |
| 无明确归属的笔记、旧计划或未验证架构 | 保留原位或约定的旧资料区 | 保留来源和未验证身份，不默认为垃圾 |

`spec.md`、`plan.md`、`log.md`、`evidence.md` 及“规划/进度/决策”等名称可提示工作文档，但也可能属于业务功能或产品手册；核对入口和正文后再迁移。Schema 4 的单页 README 已可承载小工作项，不为了分类强行拆成五个文件。

WORK、HISTORY 和工作项管理入口由 README 数据派生。散落的进度或历史文档需要先归入正确工作项或保留为旧资料，不能直接合并进派生受控区块。

## 内容核对

文件较大时先读标题、元数据和开头，再按疑点检索或读取相关章节；前 50 行可用于初筛，不能代表整个文件已经核对。关注下面的区分：

- “验收、Stage、下一步”通常提示工作过程；“安装、使用、API”通常提示产品说明。
- “计划中、拟采用、待验证”不能成为 Current 的实现事实。现成架构文档结构上适合 Framework，也可能需要留在旧资料区待验证。
- CHANGELOG 的用户可见版本变化属于产品历史；开发过程、阻塞和交接属于工作记录，不能仅按名称合并到 HISTORY。
- 当前实现架构与产品使用说明可能引用同一实现，但维护各自读者所需信息，通过链接指向事实来源而非重复整篇正文。

一份文档同时包含产品说明和工作过程时，优先根据主要职责整体归类。确有可独立阅读的章节且本次范围涵盖拆分时，保留内容、来源映射和必要链接后拆分；不能因为存在两个 H2 就自动拆分。存在会改变内容含义的歧义时保留原文并说明待定点。

## 整理深度

这些是范围描述，用户已有选择时直接沿用，不要求再次选择档位。

| 深度 | 操作范围 |
|---|---|
| 只加工作区 | 添加必要治理入口与工具，已有代码和文档保留原位 |
| 归位工作文档 | 在前者基础上，移动范围已明确的工作文档；不重组代码 |
| 完整重组 | 按已确认布局移动项目代码、文档与配置，同时修复受影响引用并实际测试 |

已有工作区只补缺失文件时走更新路径；需要移动、改名或删除时走重构路径。monorepo 默认保留子项目独立边界，工作项可关联路径；纯文档项目也可使用相同工作区，无需创建空后端或前端目录。

## 迁移核对

在执行前给出简短的源到目标映射，检查目标冲突、同一文件是否有重复建议、排除项是否误入。代码或配置被移动时检索 import、构建、CI、运行配置和测试中的引用；只读模式只报告建议。

迁移后核对实际文件、内容保留情况和全部受影响入口。共享 Spec 指向一个已登记主工作项，其他工作项引用该 Spec，并各自保留范围、依赖和验收结果；不要为迁移生成空 Spec 或虚构依赖。按 [一致性检查规则](consistency-check.md) 运行工具，项目测试和构建失败时不能报告完整迁移成功。

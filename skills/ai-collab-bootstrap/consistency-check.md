# 一致性检查规则

接入、对齐、升级及其中必要迁移需要验证时读取本文件；项目日常检查由本地协议和工具承接。结构合同以目标项目的 Policy、Lifecycle 和实际工具为准；新安装参照 [Policy 模板](templates/workspace/docs/DOCUMENTATION_POLICY.md) 与 [Lifecycle 模板](templates/workspace/docs/DOCUMENT_LIFECYCLE.md)。规则与工具冲突时保留实际错误，不通过改记录绕过检查。

## 统一入口

在目标项目根目录运行：

```bash
python3 workspace/scripts/maintain.py --check
```

这是只读检查，不刷新视图、不补文件、不写工作记录。没有相应对象时说明不适用；尤其无 Git 仓库时不能伪造提交哈希或把 Git 检查写成通过。

发生实际变更并需要交接或阶段收口时，针对已登记工作项运行：

```bash
python3 workspace/scripts/maintain.py --checkpoint TASK-01
```

检查点入口刷新派生视图、运行完整治理检查并记录该次工具实际结果。它不会提交、部署或替模型完成业务验收。小工作项的结果可留在 README 的验证区；复杂工作项按需使用 Log/Evidence。不要同时维护相同结果的多份清单。

机械字段、原件导入及章节链接优先使用项目内维护辅助命令，接口以 [Lifecycle](templates/workspace/docs/DOCUMENT_LIFECYCLE.md#机械字段、附件与链接)为准。辅助工具不选择业务结论：核对范围和授权、适用证据、完整 AC 后由执行者显式设置状态。记录仅含任务事实和必要链接，长规则仍从项目协议读取。

## 判定范围

| 检查对象 | 要求 |
|---|---|
| 必要入口与模板 | 根入口、三份本地规则、五份模板库存、工作项目录与日常工具存在；固定 project/docs、framework、路线与决策骨架不作为必需条件 |
| 工作项 | 元数据、稳定 ID、状态、Stage、依赖和引用符合该 Schema 合同；拒绝依赖循环、未知引用与非法状态 |
| 阅读和交接 | 目标、范围、验收条件、下一步和实际验证可定位；小任务单页即可，复杂项通过明确链接查找拆分文档 |
| 现行约定与附件 | 新授权/范围回流 Spec 或范围章节，安排与准入条件回流 Plan 或计划章节，实际结果进入 Evidence 或验证章节；附件有独立用途、分类与批次入口，保留原件与历史结论 |
| 终态证据 | 完成或取消有可复核结论和实际证据；历史兼容入口可读，不能自动完成或改写旧结论 |
| 证据与接手成本 | 首败及后续结果从项目内入口可达，源码/输入及实际覆盖可定位；外部原件注明限制，重复规则和长历史不妨碍当前范围/下一步 |
| 稳定文档 | 已有导航/登记及 Markdown 目标和锚点有效；原生稳定文档沿用格式，显式架构角色和引用正确 |
| 项目文件布局 | 根/模块入口能定位目录职责；新增、生成和改名文件在模块内分类、命名，版本有真实含义，临时代码有去向，测试与运行入口可发现 |
| 修复与验证方法 | 处理深度与影响/风险相称，复发或回退有必要重评估，旧证据说明适用依赖，修复依据真实合同，结果与经验可定位 |
| 派生视图 | WORK、HISTORY（及已有旧管理入口）与来源记录一致，人工区保留，受控区块只由工具生成 |
| 本次差异 | 没有带入用户文件、敏感信息、缓存、无关内容或格式错误；项目代码移动后另跑实际测试和构建 |

Schema 2/3 保持兼容，不强制迁移字段或五文件记录。Schema 4 新项采用单页工作项，只有信息量或实施复杂度需要时拆 Spec/Plan/Log/Evidence，不要求固定十类影响矩阵。共享 Spec 的相对链接必须指向其他已登记工作项的实际 `spec.md`，不能仅修字段让错误目标消失。

检查工具只验证其实现的结构合同。文件职责是否错位、架构陈述是否真实以及测试是否覆盖验收条件，还需要读取相关内容与运行结果；不能把名称启发式或工具退出码当作这些判断的全部依据。

按[项目文件布局](templates/workspace/docs/PROJECT_LAYOUT.md#检查点核对)审查本任务新增、改名和未跟踪文件，并覆盖相对任务基线已提交的变化。核对内部分类、命名、版本含义、重复实现及临时代码去向；移动后核对实际受影响的导入、测试支持与收集、资源加载、构建/部署和 CI 选择。该项由执行者结合实现完成，当前维护工具不自动判定代码职责。

结构检查覆盖活动 Schema 4 项的散落 JSON 等产物、附件分类目录和从 README 进入的正文索引。回流是否充分、多个“最新”约定是否互相冲突、证据是否适用于当前源码需人工读取核对；不能通过标题关键词、文档数量或新增总结文件冒充完成。授权来源已有稳定引用时直接使用，迁移独立原件时同步生成/读取路径并保持内容哈希。

## 修复与失败

授权内的可逆修复直接执行，例如修合法元数据、补必要骨架、修链接和重生成派生区。不能手改派生结果掩盖来源问题，不能用模板覆盖已验证事实、无关用户内容或历史证据。

原地更新不移动、改名或删除已有文件。需要这些操作时核对既有授权；已有整理授权覆盖则进入相应重构范围，范围不明或会丢失无法恢复内容时再确认。Git 提交、破坏性重置、部署、第三方权限及付费不由检查流程授予。

按 [Lifecycle](templates/workspace/docs/DOCUMENT_LIFECYCLE.md#按问题范围修复与验证)选择定点处理或扩大诊断，不因一次普通失败默认全仓审计，也不对高风险或反复失效持续叠加补丁。无新证据或可检验假设时重新评估方向或报告阻塞。结合实际合同审查样本特例、校验变更及相邻反例；按 [Policy](templates/workspace/docs/DOCUMENTATION_POLICY.md#修复经验与验证复用)核对旧证据复用和经验落实，保留原失败。上述判断由执行者完成，不增加正文关键词、固定重试次数或统一测试数量门禁，项目既有验收和预算要求仍适用。

严重错误在当前范围修复并重跑相关检查；无法修复时保留未关闭状态，写明错误、影响和恢复入口。不要在非交互场景默认接受所有修复，不以跳过、登记豁免或缺少运行环境改称通过。

## 报告

报告聚焦修改结果与影响，附实际运行的命令、结果和未验证范围。区分通过、失败、未运行和不适用；需要外部条件才能继续时给出具体下一步。治理检查、业务验收和迁移后的运行验证各按实际证据表述。

## 模板源发行

本 Skill 的 `templates/` 是主模板的可携带发行件。仅在维护模板源仓时使用该仓根目录的 `python3 scripts/sync_templates.py --write/--check` 单向生成与核对，并按贡献说明核对规则入口；实例化项目不把它作为日常步骤。发行件保留入口、模板和实际工具，排除真实工作项、用户文档、人工日志、缓存与私有数据。禁止手改副本后反向覆盖源仓。

升级验收还要核对根/模块 README、AGENTS、Workspace/WORK/现存导航、三份规则、五模板与创建回退、工具、治理来源记录，确认项目日常脱离全局 Skill 仍可运行。发行同步只生成模板副本，不会自动更新上述人工说明或已安装项目。

既有项目的定制比较依 [升级方法](references/workspace-upgrade.md)，包括维护工具新增模块的部署；旧工作项默认只读。完整多正文拆分、启动兼容和真实客户端行为只有实际运行过才写通过；未安排验证时保留缺口，不引用旧评分提升当前结论。

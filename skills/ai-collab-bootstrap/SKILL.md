# AI 协作工作区引导

把项目的稳定代码与产品说明留在项目侧，把工作范围、下一步和验证记录放在 `workspace/`。结果应便于人类阅读、AI 接手和证据核对，同时减少日常填写与重复确认。

安装位置与各客户端的调用方式见 [Agent 接入](references/agent-setup.md)；只在安装或排查加载问题时读取。本 Skill 使用标准 SKILL.md，不绑定某个编辑器。目标项目只维护一份 AGENTS.md；CLAUDE.md、GEMINI.md 等工具入口可以薄引用该协议，不复制规则。

## 共用边界

- 先读取目标项目的根协议和入口，沿现有工作项找到范围与下一步。内容归属以项目的 `DOCUMENTATION_POLICY.md` 为准，记录与流转以 `DOCUMENT_LIFECYCLE.md` 为准；新建项目使用本 Skill 自带的同名模板。
- 用户已经选择模式、明确范围或授权操作时沿用这些决定。授权内的可逆整理直接完成；只有缺失信息会改变范围、会丢失无法恢复的内容或操作超出现有授权时才确认，不强制逐轮问答。
- 不覆盖用户或协作者改动，不读取或搬运密钥、私人数据、依赖缓存或本地数据库；人工专用开发日志沿用项目协议，不能因套模板改写。
- 不自动提交、推送或执行破坏性 Git 重置。较大迁移先核对可回退基线，并保留受影响的未提交内容；修复只恢复本次操作，不能抹掉其他改动。
- 已实现架构只写可由代码、配置、测试或运行证明的事实；稳定产品说明放在项目文档中。已接受的未来目标可按需放入 Target，未经验证的设想保留为候选或旧资料。
- 项目测试与验收要实际运行并读取结果。结构检查通过只证明治理结构通过；未运行、失败和不适用分别说明，不自动完成工作项或部署。

## 选择处理路径

先根据用户请求和目录现状选择路径；没有明确请求时仅给建议，不擅自扩大任务。

| 路径 | 适用情况 | 完成结果 |
|---|---|---|
| 新建 | 尚无工作区，用户要求安装协作结构 | 按项目实际需要生成入口、记录模板和检查工具 |
| 更新 | 已有工作区，只需检查、补齐或升级 | 原地修复缺口，保留已有目录、工作项与历史 |
| 重构 | 需要移动、改名或收敛混合文档 | 在约定范围内归位文件，修复受影响引用并验证 |

仅检查时使用只读入口，不创建工作项、迁移状态或模板文件。

## 新建

项目名称、定位和代码布局优先从现有入口获取，只询问不能合理推断的关键缺口。代码已有成熟布局时保留布局；技术栈不决定必须创建哪些空目录。

从模板源按相对路径复制治理入口、工作项模板和工具，按项目事实实例化名称、日期和使用说明，保留模板文件自身的占位符。Current 尚无实现事实时保持简短空骨架；Target、ADR、详细架构页和产品文档正文按实际需要创建，移除未创建文件的所有导航与元数据引用。

无冲突的新目录可运行 `python3 <本Skill目录>/scripts/bootstrap.py --target <项目目录>` 预览，加 `--write` 复制骨架。脚本不实例化项目事实；已有 README、协议或工作区时不要覆盖，按当前新建/更新路径合并必要内容。安装 Skill 不等于为目标项目安装工作区。

先说明本次新增或修改范围；已有授权覆盖这些可逆操作时继续执行，不再次要求批准同一份范围。需要创建工作项时，优先使用 [维护入口](templates/workspace/scripts/maintain.py)：

```bash
python3 workspace/scripts/maintain.py --new TASK-01 --title "明确的工作目标"
```

新 Schema 4 小工作项只需 README，内含目标、范围、验收条件、下一步和实际验证；复杂任务才拆 Spec/Plan，Log/Evidence 按信息量和交接需要拆分。无 Git 项目不伪造分支或提交哈希，Git 检查记为不适用。具体合同以 [Lifecycle 模板](templates/workspace/docs/DOCUMENT_LIFECYCLE.md) 为准。

## 更新

按 [一致性检查规则](consistency-check.md) 先读检查结果，再修复本次范围内的入口、合法元数据、缺失骨架和链接。旧 Schema 2/3 记录保持可读，不为了统一版本批量迁移历史。

WORK、HISTORY 和工作项管理入口是派生视图，修改来源工作项后由工具刷新，不能直接增删受控区块。发现需要移动、改名或删除文件时，核对是否属于已授权整理范围；不属于则报告并提出重构范围，不在“原地更新”中偷偷搬文件。

模板升级只补项目实际需要的结构，不能用模板覆盖项目已验证事实或改写终态历史。共享 Spec 可以指向其他已登记工作项的 `spec.md`，保留实际依赖关系和各项独立的验收结果。

## 重构

读取 [文件分类规则](classification-rules.md)，给出源路径、目标路径和分类理由。按已确认范围选择最小必要深度：只加工作区、归位工作文档，或完整重组项目目录；不因检测到代码就自动选择完整重组。

范围内自主完成可逆移动和内容归位；不确定归属可先保留原位，或在用户已接受的旧资料区保留来源说明。较大迁移保留文件映射与完成状态，恢复时核对实际文件而非盲信状态标记。

文件移动后修复 Markdown、代码 import、构建、测试、CI 和运行配置中受影响的路径。在授权范围内完成这些修复并运行原项目适用的测试与构建；缺少依赖或外部条件时记录未验证范围、失败信息与下一步，不能只搬文件后宣称迁移完成。生产部署、第三方权限或额外付费仍依目标项目协议处理。

## 验证与交接

日常只需一个入口，详细判定和失败处理见 [一致性检查规则](consistency-check.md)：

```bash
python3 workspace/scripts/maintain.py --check
python3 workspace/scripts/maintain.py --checkpoint TASK-01
```

`--check` 只读；`--checkpoint` 刷新派生视图、运行完整检查并把实际工具结果记入指定工作项。业务验收结果另行记录。失败时保持当前工作未关闭，在同一范围修复；最终报告修改结果、实际检查及剩余缺口。

## 模板来源与发行

默认模板在 [templates/](templates/)，可用 `AI_COLLAB_TEMPLATE_DIR` 指定另一完整模板目录。源缺失或不完整时报告缺口，不猜测本机目录或编造架构内容。本 Skill 可独立携带，不依赖原模板仓的绝对路径。

模板源仓是发行件的唯一来源。维护模板源时使用该仓的单向同步工具生成、检查 `templates/`；不要把真实工作项、用户文档或人工日志放入发行件，也不要反向复制发行件覆盖模板源。实例化项目的日常维护无需执行发行同步。
